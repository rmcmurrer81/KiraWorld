## Acceptance blockers

### Blocker 1 — direct CLI turns a closed gate into a Marinette turn

`tools/temporary_ai_live_chat.py` creates the run monitor and JSON before proving owner-text readiness. At lines 1999–2004, `run_chat()` catches every non-connection exception from `ask_model()` and converts it into a text string. Lines 2005–2027 then run character repair, artifact finalization, person-turn finalization, and print that string under the candidate's display name. Lines 2033–2062 normally append it to the transcript and person evidence.

The no-write hostile probe supplied one owner question and then `/quit`. Exact observed displayed output:

`Marinette / Ladybug> [TemporaryAI - error] source_grounded_text_route_blocked:fresh_independent_v3_audit_required`

The mocked trace showed `11` append calls and `2` JSON writes would occur, while exact-Qwen preflight remained uncalled. A closed model gate is therefore not a closed text/person-evidence gate.

This is not a live model failure. It is deterministic direct-call behavior in the exact audited code.

### Blocker 2 — shell direct reply returns a generic first-person fallback

`tools/kira_world_shell_server.py` calls `ask_model()` at line 7312. The exact readiness gate raises before model preflight. Lines 7365–7369 catch that exception and call the generic `reply_for()` fallback for every non-Kira candidate.

With all log writes mocked, the exact current candidate returned:

`I'm here with you in the private text-and-voice chat. I don't have a body or physical location in this launcher, so I want to answer without inventing one.`

The mocked trace recorded one failure-log call and zero model-preflight calls. The ordinary activation endpoint blocks selection, but a direct helper call or a stale/forged active-state route can still produce person-attributed text. The checkpoint's statement that owner text remains blocked is therefore true only for the normal activation handler, not for all callable text routes.

### Blocker 3 — the future shell prompt reintroduces excluded project state and movement context

The manifest-only system-prompt function is narrow, and `ask_model()` correctly omits history for the strict V3 candidate. The shell does not pass the raw current owner message to that function, however.

`temporary_ai_reply()` constructs a larger string at lines 7258–7312 and sends that whole string as the sole user turn. The captured no-model payload contained, among other text:

- a hard-coded claim that Marinette/Ladybug is using a temporary avatar still being repaired;
- hard-coded fashion, sketching, sewing, and kindness context outside the exact V3 anchor ledger; and
- `VOLUNTARY FUTURE-BODY EXPRESSION`, inviting asterisk movement directions that the V3 runtime policy says must not be parsed or persisted.

The exact owner question appeared only after this injected context. This reintroduces project/avatar state after the strict contract builder has sanitized the candidate. It also contradicts the no-movement instruction. The focused test exercises `build_contract_bound_system_prompt()` directly and therefore misses the shell-to-model payload actually assembled by the owner route.

### Blocker 4 — semantic relevance and several scope fields are not validated

The hash-pinned exact current files contain safe values. The semantic validator is narrower than the checkpoint claims, however:

- official evidence relevance is considered present when `bounded_support` is merely a nonempty list; its statements are not matched to the exact claim;
- profile `status` and `activation_policy.text_voice_chat_allowed` are not checked;
- review voice-scope flags and `life_loop_allowed_by_this_review` are not checked; and
- source-pack status is not checked.

Deep-copy probes changing each field independently were accepted by `_validate_semantics()`. A disk edit alone is still caught by the pinned manifest, but a future coordinated manifest/code-pin update could claim semantic validation without these contradictions being noticed. This does not alter the exact current non-adult result; it rejects the stronger assertion that the validator itself proves every status and relevance boundary.

### Blocker 5 — path bytes are bound, but file identity is not

The current exact members are ordinary single-name files. An outside-project junction was rejected, and a simulated different-content substitution between resolution and open was rejected by SHA-256.

The path guard accepted an in-root junction and accepted an in-root hardlink whose second name was outside the project. There is no reparse-tag, hardlink-count, volume/file-ID, or opened-handle identity check. Same-hash content remains content-equivalent for the current prompt, and V3 does not play the no-claim media, so this probe did not expose different bytes to the model. It does mean that `all_paths_are_project_relative_and_confined` is a path-string/content claim rather than an exclusive file-identity guarantee.
